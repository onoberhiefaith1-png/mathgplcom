# MathGPL Co-Pilot — persistent lesson conversation, sequential build, textbook diagrams

Today the whole Co-Pilot conversation lives in React state inside `useCoPilotConversation`: messages, structure counts, blueprint queue and build progress are all `useState`, and the panel is lazily mounted only while Co-Pilot mode is on. That is why closing the panel, refreshing, or navigating away starts a blank chat that behaves like a brand-new lesson. Nothing about the conversation is written to the database yet — there is no Co-Pilot table.

The build loop is already sequential per item (`runBuild` walks the queue, generates the question then its solution), and `buildQueue` already skips a section whose number is 0 and numbers items as "Example 1/2/3". Those rules exist but are not durable: because progress is only in memory, a refresh mid-build loses which items were completed, so the lesson looks half-built with no way to resume.

## Part 1 — One lesson, one persistent conversation

- Every lesson note gets exactly one Co-Pilot session, keyed by the note id and owned by the teacher.
- The session stores the durable lesson state: topic, subtopic, structure counts, analysis brief, the approved blueprint (with each item's plan, diagram decision, 3D asset), per-item build state, current stage and current item.
- Every message — teacher and Co-Pilot, including blueprint proposals, revisions, approvals, failures and the build-completion note — is stored as a row in that session, in order.
- Opening the note loads the session and replays the conversation. No greeting, no structure card, no "let's start a lesson" when a session already exists: the Co-Pilot opens with "We're continuing <subtopic>. Here's where we left off," followed by the state summary and whatever is still pending.
- Closing the panel, refreshing, navigating away, logging out and back in all resume the same conversation. Persistence is per authenticated teacher, never anonymous or browser-only.
- The blueprint is never erased after generation — it stays in the session as the record of the original plan plus the edits made to it.

## Part 2 — Subtopic is the cycle boundary

- The structure card gains explicit Topic and Subtopic fields. Topic persists on the session; Subtopic is what the Co-Pilot builds against.
- Entering a new Subtopic starts a new content cycle (fresh structure → blueprint → build) inside the SAME conversation, under the same Topic. Earlier cycles stay in the history, so the Co-Pilot can still be asked about them.
- Changing the subtopic never clears the conversation and never asks for the topic again.

## Part 3 — Generation rules become structural

- Zero means skip, silently, with no substitution and no confirmation prompt.
- The requested count is exact: 3 examples produce Example 1, Example 2, Example 3 — no more, no fewer — and the numbering is generated by the app, not the AI.
- Question → solution is one indivisible unit: generate question, validate it, solve it, validate the solution, save both, then move to the next item. No batch of questions followed by solutions later.
- The order is fixed: Introduction → Explanation → Example n + Solution n → Classwork n + Solution n → Exercise → Assignment → Conclusion.
- Difficulty rises across the items of a category (the existing progression instructions carry into every item).
- After each item completes, its state is saved immediately. A failure marks only that item failed, keeps everything before it, and offers "Retry Example 2" — then continues with the next item. The lesson is never rebuilt from the start.
- The panel is never locked: each call has a bounded timeout, a visible progress line, retry, and (during a build) an interrupt that stops after the current item.

## Part 4 — Editing single items after generation

- "Change Example 2", "Make Classwork 3 harder", "Solve Example 2 another way", "Make the diagram in Example 2 clearer" each resolve to one stored item and rewrite only that item (and its own solution or diagram). Nothing else in the lesson is touched.
- A proposal made in chat is not applied until the teacher accepts it, so discussion and insertion stay separate.

## Part 5 — Textbook-quality 2D diagrams

- Diagrams are constructed, never drawn: the AI returns a construction program (points, segments, circles, arcs, angles, markers, labels with their sources) and the app solves it into exact coordinates through the existing construction engine. No raster/AI-art path for mathematical figures.
- Question and diagram come from the same structured model, so every vertex, chord, diagonal and angle named in the question exists in the figure — and every number on the figure comes from the question. A value the question never states is never drawn.
- Validation before insertion: structural (right vertices and connections), mathematical (angles, lengths, parallels, perpendiculars, true circles with points genuinely on the circumference, central vs inscribed angles at the right place), and visual (no overlapping, duplicated or stray labels; labels repositioned when crowded; adequate margin around the figure).
- Style is fixed: white background, dark clean strokes, consistent line weight, readable labels, restrained angle arcs, real right-angle markers.
- One question = one diagram, attached to the question and rendered between the question and the solution. Reuse the existing diagram object when the solution refers to it; never create a second copy.
- Editing a diagram edits the structured figure ("move C", "remove the 45° label", "show the centre"), never a fresh unrelated drawing.
- 3D stays out of this engine: the blueprint names the required existing MathGPL 3D asset and where it belongs.

## Acceptance test

Geometry / Angles at the Centre of a Circle, structure 1,1,3,3,1,1,1 → Use this structure → Proceed → blueprint lists all eleven items → approve → full lesson builds with Question → Diagram (where required) → Solution for each. Refresh: conversation and content intact. Navigate away and back: same conversation and state. "Change Example 2" edits only Example 2. "Make Classwork 3 harder" edits only Classwork 3 and its solution. New subtopic "Substitution Method" starts a new cycle under the same topic without clearing history.

## Technical notes

- **Migration** — `notebook_copilot_sessions` (one row per notebook: user_id, notebook_id unique, topic, subtopic, cycle index, structure counts jsonb, analysis jsonb, blueprint/queue jsonb, stage, current item) and `notebook_copilot_messages` (session_id, role, text, payload jsonb for proposal/run/blueprint snapshots, created_at). Both get GRANTs plus RLS scoped to the owning teacher and the notebook's org, matching the existing notebook policies.
- **State layer** — new `src/lib/lessonnotes/copilot/session.ts`: load-or-create the session for a note id, append messages, patch state, and debounce-autosave structure/queue changes. `useCoPilotConversation` is refactored to hydrate from it instead of starting at `stage: "greeting"`, and the greeting effect only fires for a genuinely new session.
- **Resume** — the hook derives the opening line from the stored stage/queue rather than re-asking the backend for a greeting; `runBuild` skips items already `done` (it already does) and now resumes from persisted state after a reload. `retryItem(key)` re-runs one item.
- **Item edits** — a resolver maps a teacher phrase to a stored queue item (label match, then AI disambiguation) and routes to a single-item regenerate/revise path that reuses the existing editor bridge calls; no whole-lesson rebuild path remains reachable from chat.
- **Diagrams** — the `mathengine` construction path (`src/lib/geometry/construct/`) becomes the only 2D source for Co-Pilot items: extend `types.ts`/`compile.ts` with the missing primitives (arcs, angle markers, right-angle markers, parallel/perpendicular ticks, label anchors with a source field), extend `validate.ts` with the label-provenance and label-collision checks, and add a label placement pass. Backend `notebook-ai` diagram prompts return construction programs only; scene output stays behind the existing one-question-one-diagram lock and `ensureOwnerQuestionId`.
- **Panel** — keep the panel mounted (state now lives outside React anyway), render history chronologically with scrollback, and keep the conversation visible after the lesson is generated.
- **Rollout** — (1) persistence + resume, (2) sequential build with per-item save/retry and subtopic cycles, (3) single-item editing, (4) diagram construction and validation upgrade.
